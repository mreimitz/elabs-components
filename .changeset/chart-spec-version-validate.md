"@elabs-ai/components-charts": minor
---

`ChartSpec` gains an optional `version` field (`1` today; absent reads as `1`) and a new `validateChartSpec(spec)` export that checks an untrusted spec — an agent's tool-call JSON, a saved dashboard tile — the way `@elabs-ai/components-ui/definition`'s `validateProps` checks component props: it never throws, and returns `{ ok, value, issues }` with the shared `SpecIssue` shape. A spec whose `version` this build does not recognise still validates, with a `"warning"` issue, instead of failing outright.

`AutoChart` inside a `ChartFrame` now hands its spec's `title` up to the frame's own header (through `useChartFrameChrome`, alongside the existing `notes`/`byline`/`source`); its own in-plot title paragraph yields to the frame's ONLY where the frame is actually the one drawing it (a `chrome="card"`, or a `chrome="tile"` with no `headerSlot`) — a bare frame, a tile with a `headerSlot`, and an explicit `ChartFrame.title` (which keeps both) still see `AutoChart`'s own title too. Most legends now come from a container's own shared legend engine (`useContainerLegend`) instead of the old internal `AutoLegend` list; `AutoLegend` itself stays as the fallback for the six container families with no legend engine of their own (candlestick, waterfall, histogram, box, strip, bump).

`validateChartSpec` also warns (never fails) when an optional field is set on a `type` that never reads it — `group` outside a histogram/box/strip spec, `y2` outside a heatmap/calendar/bump one — and derives its minimum series count per `type` from the same chart definitions, so a spec with fewer series than its type needs is now flagged too (a warning, not a failure, for the one family that still draws something real below its minimum). A new `chartTypeSummaryLabel`/`CHART_TYPE_SUMMARY_LABEL` export names every `ChartType` in plain words, with a generic fallback.
