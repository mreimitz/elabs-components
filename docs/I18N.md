# i18n: locale, plurals, and bridging to your own runtime

`@elabs-ai/components-ui` ships `LocaleProvider` / `useLocale()` — the seam every
component's microcopy, number formatting and date formatting reads through
(ADR [0014](ADR/0014-i18n-direction-and-microcopy-seam.md), ADR
[0017](ADR/0017-microcopy-adoption-and-namespacing.md)). This page covers the two
things layered on top of that seam: **cardinal-plural forms**, and a **pluggable
`translate` resolver** so an app that already runs its own i18n runtime
(next-intl, react-intl, i18next, …) can hand brand-ui its own translator instead
of maintaining a second, parallel message catalogue.

Per D5 (`docs/DECISIONS.md` §D5), brand-ui is a **presentation layer** — it does
not ship or depend on an i18n runtime. Both features below stay dependency-free:
plurals use the `Intl.PluralRules` API already built into every runtime brand-ui
targets, and the bridge is a plain callback prop, not an adapter for any specific
library.

## The resolution chain

`t(key, vars)` resolves a key through up to four rungs, in order — each one only
runs if the rung before it declined:

1. **`translate(key, vars)`** — the resolver you pass `LocaleProvider`, if any.
   Its return value is used **as-is**: no further interpolation or pluralization
   runs on it, because your runtime already did its own.
2. **`messages[key]`** — the overrides you pass `LocaleProvider`.
3. **`DEFAULT_MESSAGES[key]`** — the shipped English bundle
   (`packages/ui/src/components/locale-provider/messages.ts`), the authoritative
   list of every key a component can render.
4. **`key`** — the raw key string, so a genuinely missing translation is always
   visible (and greppable) rather than blank.

Passing no `translate` and no `messages` reproduces today's behavior exactly —
both are optional, and existing callers are unaffected.

## Cardinal plurals (`Intl.PluralRules`, no dependency)

A message in `DEFAULT_MESSAGES` or a `messages` override can be either a plain
string, or a `PluralMessage` — one string per ICU cardinal-plural category:

```ts
import type { Messages } from "@elabs-ai/components-ui";

const messages: Messages = {
  itemsSelected: {
    one: "{count} item selected",
    other: "{count} items selected",
  },
};
```

When `t(key, { count, ...rest })` resolves to a `PluralMessage`, brand-ui selects
the category with `new Intl.PluralRules(locale).select(count)`, then falls back
to `"other"` (the one category every locale defines) if the selected category
has no entry, then to the raw key if even `"other"` is missing. The selected
form is then interpolated the same way a plain string is — `{count}` and any
other `vars` keys are substituted.

```tsx
import { LocaleProvider, useLocale } from "@elabs-ai/components-ui";

function SelectionCount({ count }: { count: number }) {
  const { t } = useLocale();
  return <span>{t("itemsSelected", { count })}</span>;
}

<LocaleProvider locale="en-US">
  <SelectionCount count={1} /> {/* "1 item selected" */}
  <SelectionCount count={5} /> {/* "5 items selected" */}
</LocaleProvider>;
```

**Why `Intl.PluralRules` and not `intl-messageformat` (full ICU MessageFormat).**
`Intl.PluralRules` is built into every JS runtime brand-ui targets (Node 13+, every
evergreen browser) — zero added bytes, zero new dependency — and it covers the
plural case component microcopy actually has: "N of these things", "N item(s)
selected", "N result(s)". Full ICU MessageFormat additionally supports `select`,
`selectordinal`, nested arguments and number/date skeletons — a much larger
surface with a real dependency cost, and one this repo's own audit found no
shipped microcopy that needs (see `docs/ADR/0014-i18n-direction-and-microcopy-seam.md`
and `docs/ADR/0017-microcopy-adoption-and-namespacing.md`, neither of which found
a select/selectordinal case). If your app needs that larger surface, that's
exactly the "Better" tier the `translate` bridge below already unlocks: your
runtime's own ICU formatter runs FOR you, so brand-ui never needs to ship one.

**Locale-specific plural rules genuinely differ — always test against at least
one locale that isn't English.** English has two categories (`one`/`other`);
Polish and Russian have four (`one`/`few`/`many`/`other`) with different count
boundaries (Polish: 1 → `one`, 2–4 → `few`, 5+ → `many`; the `few`/`many` split
moves for teens and for numbers ending 2–4 vs 5–9/11–14). A `PluralMessage` that
only supplies `one`/`other` still works for those locales — the missing
categories fall back to `other` — but the result will read grammatically as if
every count that isn't singular is treated identically, which is wrong for those
languages. Supply the categories your target locales actually use.

## Bridging to your own i18n runtime (`translate`)

If your app already runs a full i18n runtime, don't flatten its catalogs into a
second `messages` bundle for brand-ui — hand `LocaleProvider` a `translate`
function instead. It receives the **raw key and vars** (never pre-interpolated),
so your runtime's own ICU formatting, pluralization and interpolation run
exactly as they do for the rest of your app:

```tsx
<LocaleProvider
  locale={locale}
  dir={dir}
  translate={(key, vars) => tFromNextIntl(`brandUi.${key}`, vars)}
>
  <App />
</LocaleProvider>
```

Return `undefined`/`null` from `translate` for any key you don't want to
override — brand-ui falls through to `messages`, then `DEFAULT_MESSAGES`, then
the raw key, so a resolver only needs to cover the keys it actually has
translations for. This is what lets extraction and parity tooling in your own
runtime keep working: brand-ui's keys are just more entries in your existing
catalog, not a separate system to keep in sync.

### Worked example: next-intl

Assume your `messages/en.json` (and every other locale file) has a `brandUi`
namespace mirroring brand-ui's key list from
`packages/ui/src/components/locale-provider/messages.ts` (the authoritative
source):

```json
{
  "brandUi": {
    "close": "Close",
    "itemsSelected": "{count, plural, one {# item selected} other {# items selected}}"
  }
}
```

Wire it up once at your app root:

```tsx
"use client";

import { useTranslations } from "next-intl";
import { LocaleProvider } from "@elabs-ai/components-ui";

export function BrandUiLocaleBridge({
  locale,
  dir,
  children,
}: {
  locale: string;
  dir: "ltr" | "rtl";
  children: React.ReactNode;
}) {
  const t = useTranslations("brandUi");
  return (
    <LocaleProvider
      locale={locale}
      dir={dir}
      translate={(key, vars) => {
        // next-intl throws for a missing key rather than returning undefined —
        // catch it so brand-ui can fall through to its own English default.
        try {
          return t(key, vars as Record<string, string | number>);
        } catch {
          return undefined;
        }
      }}
    >
      {children}
    </LocaleProvider>
  );
}
```

Now `itemsSelected` is pluralized by next-intl's own ICU MessageFormat engine
(which understands `{count, plural, one {…} other {…}}` syntax directly), using
the same `messages/*.json` catalogs, extraction tooling and translator workflow
your app already has for everything else. The same pattern applies to
`react-intl` (`useIntl().formatMessage({ id: \`brandUi.${key}\` }, vars)`) and
`i18next` (`i18n.t(\`brandUi:${key}\`, vars)`).

## RTL direction needs no extra work here

`dir="rtl"` is unrelated to either feature above and already fully wired:
`LocaleProvider` wraps its subtree in Radix's `DirectionProvider` so portalled
overlays (Dialog, Sheet, Popover, DropdownMenu, Select, Tooltip, …) inherit
direction from context rather than DOM position, and `packages/tokens/src/rtl.css`
carries the logical-property overrides raw utilities don't cover automatically.
See ADR [0014](ADR/0014-i18n-direction-and-microcopy-seam.md) for the full
mechanism. A locale that needs RTL needs nothing beyond
`<LocaleProvider dir="rtl">` — no interaction with `translate` or plural forms.
