# Storybook (elabs-ai.com) + hosted MCP review — 2026-09-17

Scope: the live deployment at `https://elabs-ai.com` (Storybook 10 static build of `apps/docs`, release 4.2.0 — the version the hosted MCP reports) and the hosted MCP at `https://elabs-ai.com/mcp`. Two audiences were held in mind for every page: a **first-time visitor deciding whether this library is worth adopting**, and a **coding agent that has to get from "I heard of brand-ui" to "I produced a correct, on-brand screen" without a human**.

Method: every entry in the live `index.json` (2,314 entries: 1,954 stories, 360 docs pages, 381 component titles in 25 top-level groups) was opened in headless Chromium against the live site, one story per page, with console, page errors, failed requests, rendered-DOM checks and a screenshot captured per story; every docs page was opened the same way (against a local dev server built from the same commit, `80f92e8e`) and its H1-to-first-preview text, props table, embedded story previews and rendered markdown were checked. The 75 stories that looked wrong in the crawl were re-opened individually with a 5-second settle to separate transient CDN failures from real defects. Each of the eleven `Docs/*` pages was read in full at 1440×900 in the Storybook shell. The hosted MCP was exercised with raw JSON-RPC (`initialize`, `tools/list`, every tool, an unknown component, an unsupported method, `GET`). Repo claims were verified against source. Findings that could not be reproduced individually are marked **transient** and are not counted as defects.

Related earlier reviews: `docs/review/2026-06-15-storybook-ia-review.md`, `docs/review/2026-09-03-storybook-ia-and-ambiguity-review.md`. This review does not repeat their IA findings; it covers what a visitor and an agent actually get today.

## 1. Executive summary

The library is far bigger and better than its front door says. The stories themselves are in good shape — 1,899 of 1,954 render cleanly, the visual language is consistent, dark/light and the Qlik/Ocean/Snowflake families work, the toolbar dials (theme, mode, decoration, motion, density) are real. What fails is the **packaging**: the first three pages a visitor reads are broken or stale in ways that undercut the credibility the components earn, and the hosted MCP — the strongest agent-onboarding asset the project has — is not linked from anywhere a visitor or an agent would look.

Ranked by impact:

1. **P0 — Markdown tables do not render on the customer-facing docs pages.** `Getting Started`, `brand-ui MCP Server`, `AI Output Contract`, `View Toolbar Contract`, `Choosing between similar components` and `Patterns/Blocks/KPI Cards/Which KPI card?` all show raw `| --- | --- |` pipe text (six pages). Cause: `@storybook/addon-docs` is not configured with `remark-gfm`, so GFM tables are plain paragraphs. The very first table on `Getting Started` is the "Pick your path" router — the page's whole purpose — and it is unreadable. **Fixed in this pass** (§7).
2. **P0 — 7 stories crash in production with `Cannot read properties of undefined (reading 'customEqualityTesters')`.** `AI/Reasoning` (4 stories) and `AI/Sources` (3 stories) show the Storybook error overlay instead of the component, live and locally. Cause: `reasoning.stories.tsx` and `sources.stories.tsx` import `expect` from `"vitest"` instead of `"storybook/test"`, so vitest's node-only expect is evaluated in the browser bundle at module load. Two of the flagship chat primitives (reasoning, citations) therefore have **no working story at all**. **Fixed in this pass.**
3. **P0 — 26 chart stories render an empty canvas, `Charts/BarChart/Default` and `Charts/LineChart/Default` among them.** In the story canvas (not the docs page) the SVG mounts with zero marks — measured on the live site, on a production build, and confirmed in the desktop browser on your Mac (`#storybook-root` 32 px wide, wrapper 0 px). Cause: the global `layout: "centered"` makes `#storybook-root` a shrink-to-fit flex item of the centred body, so a wrapper sized `w-full max-w-[…]` — exactly what the `no-fixed-story-wrapper` gate tells authors to write — resolves to 0 px and the chart's `ResizeObserver` draws nothing. Every chart story with that wrapper is affected (BarChart 2, LineChart 2, BulletChart 5, DumbbellChart 5, TreemapChart 3, BumpChart 2, DistributionChart 2, WaterfallChart 2, Choropleth, Sankey, Scatter — Appendix D). Nobody noticed because the docs page, which is not centred, renders them fine. Several of their `play` functions fail on the live site (`expected null not to be null`), which shows the Storybook test run is not gating what ships. **Fixed in this pass** with one CSS rule in `preview.css` that gives the centred root a definite width (§7).
4. **P0 — The "Dark" mode toggle does nothing visible on docs pages.** Selecting Dark puts `data-theme="dark"` on the iframe root, but the docs container and every embedded preview keep Storybook's light docs theme and a white preview background, so the Button on `Core/Button/Docs` looks identical in Light and Dark. A visitor who came for "themeable to any brand" toggles the one control that would prove it and sees no change. Cause: no `DocsContainer` override — the docs theme is never derived from the resolved `data-theme`. **Fixed in this pass**: a `ThemedDocsContainer` that follows the root's `color-scheme`, plus `.sbdocs-wrapper`/`.docs-story` painted with `--background`/`--foreground` (§7).
5. **P1 — The hosted MCP is invisible.** `https://elabs-ai.com/mcp` works well (stateless Streamable HTTP, CORS, five tools, correct JSON-RPC errors), but it is mentioned in exactly one place in the whole repo: `packages/cli/README.md`. Not in `Docs/brand-ui MCP Server` (which says transport is stdio only), not in `Getting Started`, not in `README.md`, not in `llms.txt`. The page that is supposed to route agents (`Docs/Storybook MCP for Agents`) still says the CLI is "a private GitHub Packages dependency" needing "one-time auth setup" and points at `localhost:6006/mcp`, which does not exist on the hosted site. **Docs fixed in this pass**; `llms.txt` generator fix is listed in §6.
6. **P1 — `llms.txt` on the live domain is stale and self-contradicting.** It says "install from GitHub Packages", "Themes (2)", "Live MCP (dev): localhost:6006", and offers no hosted endpoint — an agent following `https://elabs-ai.com/llms.txt` is sent to a private registry that no longer exists. The generator (`packages/cli/lib/render-docs.mjs` lines 239–275) hard-codes the stale text. (§6, B1.)
7. **P1 — Component docs pages carry none of the intent the MCP knows.** The manifest holds purpose, relationships, state-token map and anti-patterns for 190 components (`brand-ui docs Button` returns them), but the Storybook page for Button shows an H1, a preview and a four-row props table — no description, no import line, no "used inside / pairs with / avoid", no link to the MCP. 68 of 349 component docs pages have **nothing at all** between the H1 and the first preview (all of Core/Forms/Overlays primitives among them). The two audiences are being served from two different sources that never meet. Fix: a manifest-driven `Intent` docs block rendered on every autodocs page (§6, A1).
8. **P1 — Internal QA content sits in the customer-facing front section.** Of the eleven `Docs/*` entries, five are not for customers: `Storybook Theme Harness` and `Storybook Motion Harness` are regression guards for issues #402/#125 ("This story only asserts a harness invariant"), `Testing Charts in jsdom` is a consumer-test recipe, `View Toolbar Contract` is an internal-app design rule, `AI Content Access` is a release note ("CodeWorkspace breaking change"). Across the tree, 52 story names carry issue numbers, ADR numbers, "regression lock", "hit test", "perf harness", "Css Check"; 47 stories exist only as `— dark` / `— high decoration` / `compact density` duplicates of another story, which the toolbar already provides. **Harness pages hidden in this pass**; the rename/`!dev` list is in Appendix A.
9. **P1 — Page metadata is Storybook's default.** `<title>` is "Docs / Introduction - Docs ⋅ Storybook" (static HTML: "storybook - Storybook"), there is no `<meta name="description">`, no Open Graph/Twitter card, no `robots.txt`, no `sitemap.xml`, `/favicon.ico` is 404. Shared links unfurl as "Storybook". **Fixed in this pass** (managerHead + title shim).
10. **P2 — Stale or contradictory facts in the front pages.** Intro: "Switch themes with the toolbar (sun/paint icon): Light and Dark" — the toolbar is _Theme family × Mode_ and ships Default, Ocean, Qlik, Snowflake (Salesforce/Heap are on `main`, not yet released). Getting Started Path A: `/plugin marketplace add <path-to-this-repo>` — a visitor has no path; the marketplace at repo root means `mreimitz/elabs-components` works. `Storybook MCP for Agents` says "Themes (three; default light)" and has a "To add it manually:" heading followed by nothing. `AI Output Contract` has two "the data the agent emits:" lead-ins whose code blocks are missing on the rendered page. README says "Twelve packages" (there are thirteen — terminal and process are missing from the table). **Front-page copy fixed in this pass.**
11. **P2 — Controls warnings on 21 stories** (`Control of type color only supports string, received "function"/"union"`): the global `controls.matchers.color: /(background|color)$/i` catches props like `color` that are typed as functions/unions. Narrow the matcher or set `control: false` per prop.
12. **P2 — Twelve chart docs pages leak raw JSDoc tags** (`@dataShape … @avoidWhen …`) as the component description: the tags that feed `chart_for` are shown verbatim to visitors. Either render them as labelled rows ("Best for / Avoid when") in the Intent block or strip them from the docgen description.
13. **Observed, not a defect: transient 502s.** Under an 8-way parallel crawl, Vercel returned `502 Bad Gateway` for 20 asset chunks (each story affected loaded fine when reopened alone). Worth knowing if a customer ever reports "the component failed to render" once and never again.

What is **good** and should stay: the sidebar order (Docs → Foundations → primitives → domain packages → Patterns) reads well; Foundations pages are genuinely educational (Colors, Elevation, Motion, Decoration, Paper); the Patterns/Templates and KPI-card question pages ("Should I act?", "What changed most?") are a differentiator no competitor has; `Choosing between similar components` is exactly the page an agent needs (once its tables render); the toolbar dial set is unique; `AttributionPanel` as a shipped component is a classy touch; the hosted MCP's `docs` output (purpose, anti-patterns, expanded cva variants) is better than most libraries' human docs.

## 2. The Docs section, page by page

### 2.1 Introduction (`docs-introduction--docs`)

This is the landing page (Storybook opens it by default). It is a package list, not a pitch. Compared with the repository README — which opens with "Most component libraries give you buttons and inputs, then leave you to invent the hard parts. brand-ui ships the hard parts" and a highlights list — the Storybook intro is the weaker of the two, and it is the one a visitor sees.

Specific problems: the first sentence positions the library "for internal apps, prototypes, POCs" — the wrong register for a public library that memory and README both say is meant to be a public, shadcn-like system. "Switch themes with the toolbar (sun/paint icon): Light (default) and Dark" describes a toolbar that no longer exists; the live toolbar is _Default ▾ / Light ▾_ and offers four families. There is no screenshot, no live component on the page, no "why", no link to the hosted MCP, no link to the `Getting Started` page (the three links go to GitHub). All thirteen package bullets are generated — good — but the "Full guide" links leave the site.

Recommendation (partly applied, §7): open with the README's value statement, add a one-line "for agents" callout with the hosted MCP command, correct the theming paragraph, link to Getting Started and Choosing-between-similar-components in-site, and embed one live composition (the Dashboard template story) so the page shows the library instead of listing it.

### 2.2 Getting Started (`docs-getting-started--docs`)

The best-written page in the section and the most damaged by the table bug: both routing tables ("Pick your path", "The bundled offering") were pipe soup. Content issues once the tables render:

- Path A's install command is `/plugin marketplace add <path-to-this-repo>`. An external reader cannot follow it. The repo-root `.claude-plugin/marketplace.json` with `source: "./"` means `/plugin marketplace add mreimitz/elabs-components` then `/plugin install brand-ui@brand-ui` is the real route.
- Path C lists the stdio MCP and the Storybook dev MCP but not the hosted one — the one route that needs no install.
- Internal tokens leak: "VP-02", "issue #31", "(ADR 0027)". A visitor does not have the issue tracker.
- "Two themes ship: light (default) and dark" contradicts the toolbar.
- The "Commands & when" table is excellent for agents and should also be what the MCP `info` tool prints.

### 2.3 brand-ui MCP Server (`docs-brand-ui-mcp-server--docs`)

Accurate about the stdio server, silent about the hosted one — the comparison table row "Transport: stdio" is now wrong. The "Try it without an agent" `printf | npx` example is a nice touch; a `curl` against `https://elabs-ai.com/mcp` belongs next to it. The page also says "the five tools" and lists `info/search/docs/tokens/audit`; the server actually exposes `chart_for` too (six locally, five hosted with `audit` swapped for `chart_for`). Fixed in §7.

### 2.4 Storybook MCP for Agents (`docs-storybook-mcp-for-agents--docs`)

Everything on this page is about `localhost:6006`, which is meaningless on the hosted site — but the page is the third "agent" entry a visitor sees. Concrete defects: the "See also" bullet still says the CLI is "a private GitHub Packages dependency — see docs/CONSUMING.md §1 for the one-time auth setup" (false since the npm move); "Themes (three; default light)" is wrong twice; "To add it manually:" is followed by no code. The page should open with one paragraph saying _this MCP exists only when you run Storybook locally; on elabs-ai.com use the hosted brand-ui MCP_, then keep the rest for contributors. Fixed in §7.

### 2.5 AI Output Contract for Agents (`docs-ai-output-contract-for-agents--docs`)

Generated from the manifest — good — but two code blocks referenced by their lead-in sentences ("The data the agent emits (a `UIMessage[]`…):" and "Map each turn's parts onto the components…:") do not appear on the rendered page, and the three tables were broken. Once tables render this is a strong page. Check the generator emits fenced blocks with a blank line before them (MDX 3 needs it).

### 2.6 AI Content Access (`docs-ai-content-access--docs`)

A release note ("CodeWorkspace breaking change: the forwarded ref changed…") plus two Monaco/Milkdown demos, placed as the sixth item of the front section. It belongs under `Editor/` as `Editor/AI Content Access`, and the breaking-change paragraph belongs in the CHANGELOG. The docs page also logs `ModelService: Cannot add model because it already exists!` (two Monaco models with the same URI across the two demos) — harmless, but it is the only console error on any docs page.

### 2.7 View Toolbar Contract (`docs-view-toolbar-contract--docs`)

Good content ("what you are looking at on the left, what you can do about it on the right") but written as an internal rule for "one consuming app … across about 40 routes". It should live at `Layout/ViewToolbar` as that component's docs page (the component already has one), not as a top-level Docs entry. Tables were broken.

### 2.8 Testing Charts in jsdom (`docs-testing-charts-in-jsdom--docs`)

Useful for consumers who test with Vitest — keep it, but as `Charts/Testing in jsdom` (or a "Guides" group), not in the first-impression list. It opens with an incident narrative ("a fully green test suite has shipped a RangeError…") that reads as candid to a contributor and as alarming to a buyer.

### 2.9 Storybook Theme Harness / 2.11 Storybook Motion Harness

Regression guards for #402 and #125. Their only rendered content is "This story only asserts a harness invariant in its play function." They must stay (the test run needs them) but must not be in the sidebar: tag them `!dev` (Storybook keeps `!dev` stories in the test run and out of the sidebar) and move the title to `Internal/…`. Done in §7.

### 2.10 Choosing between similar components

The single most useful page for an agent — decision rule first, inventory second, "If you are an agent: read the rule, pick the component, then read that component's own page" — and every one of its comparison tables was pipe soup. Once rendered it should be linked from the Introduction, from `Getting Started` Path C, and from the MCP `search` output when a query matches two families.

### 3.2 Docs pages (349 component docs pages)

- **68 pages have no description** between H1 and first preview (list: Appendix C). These are overwhelmingly the primitives a newcomer opens first: Button, Card, Tabs, Textarea, Checkbox, Select, Switch, Dialog, Popover, Tooltip, Accordion, Breadcrumb… Their manifest intent exists; it is simply not rendered.
- **90 pages have no props table.** For compound components (Dialog, DropdownMenu, Form, Select) this is expected — the `component:` in `meta` is the root and the interesting props are on children; the fix is `subcomponents` in `meta` so `ArgTypes` shows all parts. For Foundations pages it is correct.
- **12 chart pages show raw `@dataShape`/`@avoidWhen` tags** as the description (§1.12).
- **Props-table quality is high**: 2,455 prop rows, only 8 with an empty description. One systematic flaw: JSDoc that mentions an HTML tag (`<button>`, `<a>`) is rendered as HTML and disappears ("Render the child element as the button (Radix Slot) instead of a ." on Button). Escape as `` `<button>` `` in source.
- **Controls drift**: `Core/Button` `argTypes.size` lists `sm|default|lg|icon`; the real cva has `icon-sm` and `icon-lg` too (the MCP knows). Derive `argTypes` options from the manifest variants instead of retyping them.
- **Heaviest pages**: `Charts/Gantt` (68 previews), `Data/DataTable` (66), `Viewer/FileViewer` (66), `Charts/AutoChart` (58). They load in 3–4 s from a US edge, acceptable, but a "Stories" section with 60+ live canvases is a scroll wall; Storybook's `docs.story.inline: false` for the heavy ones, or splitting variants into a second title, would help. Not urgent.

### 3.3 Sidebar hygiene (naming)

- **52 stories carry issue/ADR/QA vocabulary** in their visible name (Appendix A): "Ordered neutral ramp — judgeable hierarchy (#14)", "Keyboard focus indicator (#308)", "Density comparison (#394)", "Reflow Regression Lock", "50,000 marks (perf harness)", "Css Check", "With Column Resizing Sort Toggle Hit Test". A customer reads a bug tracker in the sidebar. Rule: the issue number goes in a code comment or `parameters.docs.description.story`, never in `name`; pure harness stories get `tags: ["!dev"]`.
- **47 stories are theme/decoration/density duplicates** (Appendix B) that exist so the test run sweeps a variant. They double the visible length of `Charts/HeatmapChart` (8 of 20 stories are `— dark`) and `Editor/MarkdownEditor`. Tag them `!dev` too — they stay in `test-storybook`, leave the sidebar, and the toolbar already gives a visitor the same view.
- **Very long names** (17 over 45 characters) wrap to three lines in the sidebar: "Enter Does Not Submit While The Roster Is Open", "exportSheet — light vs dark bake in different resolved colours". These are test names, not story names.

### 3.4 Sample-based visual review

Contact sheets of Foundations, Core and a random sample across Charts/AI/Layout/Process were reviewed. Consistent token use, no raw colours, no off-theme surfaces, focus rings visible. Two observations: `layout: "centered"` puts a single 36-px button in the middle of a 1280-px canvas on most primitive stories, which is standard Storybook but makes the first-click impression sparse — the docs page (not the canvas) should be the default landing for a component, which the current `Docs` ordering already does; and the App-shell stories (`Layout/App shell — Flagship`, `Dashboard`) are the strongest single screens in the tree and are buried under Layout — they deserve a place on the Introduction page.

## 4. Hosted MCP (`https://elabs-ai.com/mcp`) and the agent route

### 4.1 What works

`initialize` returns `protocolVersion 2025-03-26`, `serverInfo { name: "brand-ui", version: "4.2.0" }`, tools capability. `tools/list` returns five tools with tight schemas (`additionalProperties: false`, required fields, good descriptions — `chart_for`'s "judges the shape FIRST" is the kind of instruction an agent follows). `info`, `tokens`, `search`, `docs`, `chart_for` all answered in under a second from the manifest. `audit` is refused with a clear message pointing at the local server. Unknown component → "Buton not found. Try the search tool". Unsupported methods → correct `-32601`. CORS headers are right, `GET` is a clean 405. No `Mcp-Session-Id` — fine for a stateless server.

### 4.2 What an agent still cannot do from the hosted endpoint alone

1. **It cannot find the endpoint.** The only mention is `packages/cli/README.md`. Neither `llms.txt`, nor `README.md`, nor any Storybook page names it (fixed for the Storybook pages in §7; README and `llms.txt` are B1/B2 in §6).
2. **`search` returns repo-relative paths a remote agent cannot open.** "docs/playbooks/dashboard.md · template templates/dashboard.tsx" is right for a developer inside the monorepo and dead for an agent talking to elabs-ai.com. The hosted server should return raw-GitHub URLs (release-tagged) for playbooks and templates, or grow a `playbook` tool that returns the markdown, and a `template` tool that returns the TSX. The manifest already carries `file` and `template` per playbook — this is a formatting decision in `mcp-http.mjs`'s `hosted: true` branch.
3. **`docs` gives the API but not the usage.** No import line (`import { Button } from "@elabs-ai/components-ui"`), no minimal JSX, no link to the live story (`https://elabs-ai.com/?path=/docs/core-button--docs`). Adding `storyId` per component to the manifest at `pnpm gen` time (the story titles are known) closes the loop in both directions: the MCP links to Storybook, Storybook's Intent block links to the MCP.
4. **`info` on the hosted server is the taste profile of the docs deployment**, which it says honestly. It should also print the "Commands & when" routine from Getting Started (install → `info` → `search` → `docs` → build → `audit` locally) so a fresh session gets the route in the first call.
5. **No `getting_started`/`consume` tool.** The wiring steps (styles.css import, `@source` line, `ThemeProvider`) are the #1 consumer mistake per the docs; an agent should be able to ask for them.
6. **Discovery metadata is missing.** No `/.well-known/mcp.json` (or equivalent) and no `<link rel="mcp-server">`-style hint on the site; `llms.txt` is the conventional place and does not mention it.

### 4.3 The full agent route as it should read (target state)

1. Agent lands on `https://elabs-ai.com/llms.txt` → sees "Hosted MCP: `claude mcp add --transport http brand-ui https://elabs-ai.com/mcp`" and the per-package spokes.
2. `info` → packages, themes, taste, **the routine**.
3. `search "build a dashboard"` → playbook (with a URL it can fetch), template (URL), components.
4. `docs DashboardSheet` → props, intent, **import line, story link**.
5. Opens the story link → Storybook docs page shows the same intent block, live previews, and "Verify with the brand-ui MCP" hint.
6. Builds; runs `npx -y @elabs-ai/components-cli audit` locally; done.

Steps 1, 3 (URLs), 4 (import/story link) are the gaps.

## 6. Work list for a coding agent (ordered)

Each item is scoped to one PR and names the acceptance check.

**A. Storybook (apps/docs)**

- **A1 — Manifest-driven `Intent` block on every autodocs page.** At `pnpm gen`, emit `apps/docs/.storybook/intent.generated.json` (per component: package, purpose, category, relationships, antiPatterns, stateTokens, storyId; ~190 entries, well under 100 KB — do not import the 1.5 MB manifest). In `preview.tsx` set `parameters.docs.page` to a template `Title → Intent → Primary → Controls → Stories`, where `Intent` renders package + import line + purpose + relationships + anti-patterns + "Verify props with `brand-ui docs <Name>` or the hosted MCP". Accept: `core-button--docs` shows the purpose and the four anti-patterns the MCP returns; pages without intent show the import line only.
- **A2 — Docs pages follow the Mode toggle.** Done in this pass (§7). Follow-up: the docs container uses Storybook's stock dark/light _text_ palette on the brand _background_ tokens; consider a `create({ base, appBg: "var(--background)", … })` theme pair so headings and code blocks use brand ink too.
- **A3 — Sidebar hygiene.** Rename the 52 stories in Appendix A (issue numbers into comments/descriptions); tag the 47 variant duplicates in Appendix B `!dev`; move `Docs/AI Content Access` → `Editor/AI Content Access`, `Docs/View Toolbar Contract` → `Layout/ViewToolbar` docs, `Docs/Testing Charts in jsdom` → `Charts/Testing in jsdom`. Add a check rule that fails on `#\d+`, `ADR`, `RM-`, `harness`, `regression` in a story `name`. Accept: `index.json` has no story name matching the rule; sidebar `Docs` group has five entries.
- **A4 — `subcomponents` for compound components** (Dialog, DropdownMenu, Select, Form, Popover, Sheet, Menubar, ContextMenu, Command, Tabs, Accordion…). Accept: `overlays-dialog--docs` shows a props table per part.
- **A5 — Controls matcher.** Replace `color: /(background|color)$/i` with `/^(background|color|accentColor|fill|stroke)$/` and mark function/union-typed `color` props `control: false`. Accept: zero "Control of type color" warnings in the crawl.
- **A6 — `argTypes` from the manifest.** For components with cva variants, derive `options` from `intent.generated.json` (or `brand-ui.manifest.json` at build time) instead of hand-typed arrays. Accept: `core-button--docs` size control lists `icon-sm` and `icon-lg`.
- **A7 — JSDoc hygiene.** Strip `@dataShape`/`@avoidWhen` from docgen descriptions (render them in the Intent block as "Best for / Avoid when"); escape `<tag>` mentions in prop JSDoc. Accept: no `@` tag on `charts-*--docs` intros; Button `asChild` description ends "instead of a `<button>`."
- **A8 — Rive from unpkg.** Vendor `@rive-app/webgl2`'s wasm (`RuntimeLoader.setWasmUrl`) or gate the Rive stories behind a static fallback. Accept: `ai-plan--approved` makes no request to unpkg.com.
