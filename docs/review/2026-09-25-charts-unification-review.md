# Charts package review — verified findings (2026-09-25)

> The evidence base for [ADR 0042](../ADR/0042-chart-definitions-and-prop-groups.md). A read-only
> review (8 readers, 1 synthesis, 8 skeptic verifiers) produced these 39 findings. Copied from the
> session brief unchanged, except that the reference product is described rather than named.
> Line numbers are as of 2026-09-25 and drift as the code moves.

## Current architecture

1. Public surface: the package root packages/charts/src/index.ts (57 lines) is 10 `export *` lines. Its docblock is stale: it says '14 compositional charts', but there are about 25 containers plus Gantt, Sparkline, AutoChart and ChartMultiples. Almost everything flows through the hand-written 1041-line barrel src/charts/index.ts. That barrel exports containers, series children (Line, Area, Bar, SeriesBar, Scatter), axis children (XAxis, YAxis, BarXAxis, BarYAxis, BarValueAxis, LiveX/YAxis), Grid, ReferenceLine, TrendLine, two legend systems, the tooltip stack and most internal helpers. It renames the composable LegendItem to LegendItemComponent (index.ts:179) because chart-legend's LegendItem type already owns that name (index.ts:111).

2. Engine-level seams sit in six modules:

- chart-context.tsx: ChartProvider render context, ChartPalette/resolvePalette with CATEGORICAL_SOFT_CAP=6 (:118/:191/:127), ChartColorBy/resolveColorBy (:233/:268), Margin (:350), ChartLegendEntry (:336). Its ChartContextValue has grown bar-only fields (:509-539) and composed-only fields (:541-555).
- chart-breakpoint.ts (ADR 0039): Responsive<T> (:86), resolveResponsive (:105), ChartPlotHeight/DEFAULT_CHART_PLOT_HEIGHT (:222/:225), ChartPlotRoot/ChartPlotBox (:425/:460), warnChartOnce (:308).
- chart-config-context.tsx: host config with ChartInteractions (:28), ChartDensity xs|sm|md|lg (:47), currency, plotHeight, springs and a facet scope.
- chart-phase.ts: ChartStatus loading|ready.
- animation.ts: DEFAULT_ANIMATION_DURATION_MS=1100. It is referenced only inside animation.ts; no container uses it.
- value-format.ts plus chart-formatters.ts: ChartValueFormat defaulting to 'compact', and useChartValueFormatter / useChartValueSetFormatter (#250).

3. Prop-bundle mixins exist, but only as partial, opt-in pieces:

- ChartSelectionProps (chart-selection.ts:80)
- ChartSelectionGestureProps (selection/types.ts:81)
- ChartHoverLinkProps (chart-hover-link.ts:24)
- ChartNavigatorProps (navigator/types.ts:47) and ChartCategoryNavigatorProps (= Omit<…,'maxVisiblePoints'>, :96)
- ChartInteractionProps<TDatum> (chart-datapoint.ts:48)
- ChartA11yProps (chart-a11y.tsx:52)
- ContainerLegendProp (legend/use-container-legend.ts:68)
- ChartAnalyticsProps (analytics/types.ts:163): no family extends it.
- ChartAnnotationsHostProps (annotations/with-chart-annotations.tsx:26): used only as the generic constraint of useAnnotatedChart.

4. Feature modules pair a render side with those bundles:

- legend/: the useContainerLegend engine, plus the legacy ChartLegend, the composable Legend, RampLegend and SizeLegend.
- tooltip/: ChartTooltip, ChartTooltipBox/Content, useDefaultChartTooltip.
- labels/: label-layout, use-chart-labels, point/value/series-end/unpainted labels.
- annotations/ and analytics/: the ADR 0040 host, wired centrally through useAnnotatedChart.
- navigator/ and gestures/: one time|index window model, pinch/wheel zoom, touch-action constants.
- selection/: gesture machine that emits one ChartSelectionIntent, plus toolbar and local driver.
- chart-datapoint-layer.tsx: keyboard targets outside the SVG.

5. Only Line, Area and Composed share the cartesian engine, TimeSeriesChartInner in time-series-chart-shell.tsx (:830: scales, y-domain tween, phase orchestrator, navigator host, series mode). Three families fork their own cores instead: BarChart (bar-chart.tsx, 2136 LOC), ScatterChart (scatter-chart.tsx + scatter-chart-shell.tsx) and CandlestickChart (ChartCore at candlestick-chart.tsx:129-359).

6. How a family is assembled today:

- A forwardRef container in \*-chart.tsx declares a flat XChartProps interface that extends 0-4 mixins.
- About 25 props are restated inline (data, xDataKey, margin, animation*, reveal*, aspectRatio, plotHeight, className, status, loadingLabel, onPhaseChange, drill-down, a11y, legend).
- More blocks are declaration-merged at the bottom of the file (RM-146 restatements, annotations, analytics, tooltip; e.g. line-chart.tsx:667-705, bar-chart.tsx:2063-2111).
- Defaults live only at destructuring sites.
- A `{ tooltip = true, ...props }` wrapper calls useDefaultChartTooltip and useAnnotatedChart.
- The body then hand-wires the ChartDatapointProvider gate, useContainerSelection, useContainerLegend, ChartSelectionProvider, ChartHoverLinkProvider, the navigator/gesture objects, a hand-rolled mergedRef, and ChartPlotRoot.

7. Configuration style differs by family. Cartesian containers read <Line>/<Area>/<Bar>/<Scatter> children by displayName through per-family extract\*Configs. Pie, Ring, Sankey and Choropleth use compound children. Treemap, Network, Heatmap, Distribution, Parallel, Funnel, Bump, Dumbbell, Unit, Waterfall and Radar are data-prop-only.

8. The non-cartesian families mostly wire their own infrastructure: sizing (visx ParentSize, useLayoutMeasure, or a raw ResizeObserver), hover state, ChartTooltipBox tooltips and palette cycles. The shared layer that actually holds for them is ChartPlotRoot, useChartA11yContainerProps and the datapoint layer.

9. Serializable descriptions: the only typed serializable model is ChartSpec (auto-chart/chart-spec.ts:201-726) with a 22-member ChartType (:92-116), mapped to props by hand in AutoChart's renderChart switch (auto-chart.tsx:781-1520). Parallel copies of the chart-type set, or of ChartSpec itself, drift independently:

- CHART_TYPES (infer-chart-type.ts:75-100)
- the de-facto data-target descriptor ChartContractSpec (test/contract.ts:107-230), exposed only behind ./test
- the A2UI prose (packages/ai catalog.source.json:577)
- the parked dashboard CHART_SPEC_SCHEMA and chart-tile configForm
- the skills tables

10. Chrome belongs to ChartFrame (chart-frame/chart-frame.tsx:582-746: title/description/notes/byline/source/actions/export/table/density/loading). AutoChart reuses it only partly: it bridges notes, byline and source through useChartFrameChrome (chart-frame-context.tsx:402) but renders its own title <p> (auto-chart.tsx:2034). ChartFrame's source row is imported from the 'legacy' chart-card.tsx:42-83.

11. There is no per-chart definition object (defaults + data targets + property groups), no defaults manifest and no property-panel layer. The docs manifest is generated from the TS interfaces, but it ignores `extends`, and that is why the RM-146 restatement blocks exist.

## Strengths to preserve

- chart-breakpoint.ts is a real single vocabulary for responsive sizing: Responsive<T>, resolveResponsive, ChartPlotHeight, DEFAULT_CHART_PLOT_HEIGHT, and ChartPlotRoot/ChartPlotBox with a host plot-box. Every family except Gauge, Sparkline and Gantt uses it.
- chart-config-context.tsx already works like the layout modes and interactions of the reference chart templates: one host channel for density, interactions passive/active/select, currency, plotHeight and springs, plus a facet scope for ChartMultiples.
- ChartSelectionProps (chart-selection.ts:80) is the one prop bundle every adopter extends cleanly. The tri-state selected/associated/excluded model, resolveMarkPaint and the shared paint constants are the template other groups should copy.
- Navigator and gestures share one time|index window model. ChartScrollbarMode 'miniChart'|'bar'|'auto'|'none' matches the scrollbar vocabulary of the reference chart templates, ChartCategoryNavigatorProps is derived from ChartNavigatorProps instead of copied, and the selection engine emits one ChartSelectionIntent.
- useAnnotatedChart (annotations/with-chart-annotations.tsx:77) is the only seam wired centrally rather than per family. The ADR 0040 analytics maths are framework-free and feed annotations, derived series, legend entries, tooltip rows and domain widening from one host.
- The useContainerLegend engine (RM-118) is adopted by 11 families and already has Responsive position/layout, density hiding and analytics legend entries, so it can become the single legend group.
- value-format.ts (ChartValueFormat preset|spec, default 'compact') and useChartValueSetFormatter (#250 one unit per scale) are the right formatting primitives. RampLegend, SizeLegend and Choropleth use them correctly.
- The chart-datapoint-layer.tsx keyboard/pointer target registry outside the SVG and the generic ChartInteractionProps<TDatum> contract give a sound drill-down model. It is used by 17 families, with a test (chart-datapoint-names.test.tsx).
- TimeSeriesChartInner is a genuine shared cartesian engine for Line, Area and Composed: scales, y-domain tween, phase orchestration, navigator host and series mode.
- ChartFrame plus useChartFrameChrome is a single chrome owner (title through source, export, table, density, loading) that AutoChart already bridges into.
- ChartSpec is a typed, contract-tested serializable model (assertChartSpecContract), and ChartContractSpec is a de-facto data-target descriptor. Both are the natural seed for a registry like the one the reference chart templates use.
- The small shared primitives are solid and widely used: labels/label-layout collision engine, unpainted-labels sr-only restatement, series-markers resolveSeriesSymbols (Line, Area, Scatter), series-pattern and high-decoration, chart-hairline CHART_HAIRLINE_WIDTH, gestures/touch-action constants, ChartFallback (localized) and useChartA11yContainerProps.
- Composition over re-implementation is already practised in places: WaterfallChart composes BarChart, ChartCategoryNavigatorProps derives from ChartNavigatorProps, and Choropleth reuses ui colorScaleFor and RampLegend/SizeLegend.

### F01 [high/other] No concern-scoped prop-group layer: every container declares a flat, self-contained props interface — verdict: partly

Proposed home (pre-verification): new src/charts/props/ folder with one file per group: data-props.ts (ChartDataProps), layout-props.ts (ChartLayoutProps: margin, plotHeight, aspectRatio, className, style), motion-props.ts (ChartMotionProps), state-props.ts (ChartStateProps), chrome-props.ts. Each file exports `<GROUP>_DEFAULTS as const satisfies Required<…>` plus a resolve<Group>() function, composed into CartesianChartBaseProps / RadialChartBaseProps.
CORRECTED: There is no shared prop-group type for the data, layout, motion or status concerns. Each container declares these as flat own members with literal defaults at its own destructuring site.

The finding goes wrong in four places:

- **Prop groups already exist for other concerns.** ChartSelectionProps, ChartHoverLinkProps, ChartNavigatorProps, ChartSelectionGestureProps, ChartInteractionProps, ChartA11yProps and ChartCategoryNavigatorProps all exist. Line, Area and Composed extend four of them; Bar and Scatter extend two. The legend already has one shared prop type, ContainerLegendProp.
- **The overlap is smaller than stated.** Exactly 20 own props are common to all five cartesian containers, not about 25, and 3 of those are restated selection-gesture props. Line and Area share about 40. Scatter has no status, loadingLabel, onDatapointClick, annotations, revealOn or replayOnClick props.
- **Shared default constants do exist.** DEFAULT_ANIMATION_DURATION_MS=1100, DEFAULT_ANIMATION_EASING, DEFAULT_CHART_ENTER_TRANSITION, DEFAULT_CHART_STATUS, DEFAULT_Y_DOMAIN_TWEEN_MS and DEFAULT_CHART_PLOT_HEIGHT are all defined. The problem is that containers ignore DEFAULT_ANIMATION_DURATION_MS and inline `animationDuration = 1100` at 7 sites. xDataKey and className defaults are literals, and nothing collects the defaults per group.
- **The flat own-member restatement is partly deliberate.** Code comments (RM-146) say props are restated on each container's own interface because the brand-ui docs manifest reads own members and records `extends` without resolving it. So the proposed `extends`-based CartesianChartBaseProps would drop props from `brand-ui docs` unless core.mjs first learns to resolve inherited members.

## Reference chart templates

The reference chart templates organize chart properties in layers. An object-definition module is the stored default property tree, typed with JSDoc. A data-definition module is the data-role contract, with min/max counts, role labels and add/move/remove invariant hooks. ext/property-definition.js is the editing schema: accordion data/sorting/addons/settings, with items linked to stored properties by `ref` path. ext/styling-definitions/\* holds simple and advanced cosmetic panels that write a keyed `components[{ key, style }]` array. The explore/soft definition is a reduced viewer panel, and ext/index.js carries host integration (support, conversion, migrate adapters, metrics). Composition works in three ways. Charts reference host templates with `uses:` and override single keys. They mount factories from the shared commons package (getPluginsProperties, getDimensionUnitProperties, attributeExpression, image properties) and from sibling feature packages (scrollbar, trend-lines, forecast, custom-tooltips). And they attach function-valued attributes (show, readOnly, invalid, defaultValue, options, convertFunctions get/set, change/globalChange) that are pure-ish functions of stored properties and the computed layout. Defaults resolve in tiers: model defaults, then panel defaultValue (which may be computed from the data shape or theme), then propertyResolver's function > literal > first option > type default rule. Soft patches from getEffectiveProperties and saveSoftProperties sit on top at runtime. Commons also centralizes render building blocks (tooltip, valueLabels, refLines with refLineModel, points, lines, scroll hint, dockLayout layout modes, trellis helpers) and definitionExtender for key-based deep-merge customization. The chart-specs tool extracts each chart's schema from API specs, host JSON schemas and the legacy engine definitions. It merges them by source priority and field richness, then computes shared groups purely by normalized property path. Of 507 paths shared across 2 or more charts, the universal group is header (title/subtitle/showTitles in 31 charts, footnote in 30). After it come hypercube/dimension/measure engine groups (12-22 charts), color (14), components (14), axes, refLine and dataPoint (8), legend and orientation (7), tooltip (6), and scroll/continuous/gridline groups (3-4). The report also exposes drift a unified React library must avoid: gridLine vs gridlines, dataPoint.showLabels typed boolean vs string, labelStylingDefinition copied into 6 charts and differing only by theme key, overrideIfContinuous duplicated in bar and line, and trellis normalization duplicated inside bar. The reference table utilities show the better centralization: typed, parameterized section factories (largePanelSection({ section, getThemeValue })) that receive resolved feature booleans rather than flag names. For a React/TS library the transferable core is: per-group prop types, defaults and resolvers; one canonical path and shape per concept; a per-chart defineChart definition (data targets, groups, defaults, normalize, applicability predicates) feeding docs, Storybook controls, validation and auto-chart; keyed style slots with theme-token defaults; keyed layer extension; and a generated shared-group report with CI checks for naming and type drift. Engine-specific pieces do not carry over: hypercube query paths, soft properties and patches, engine expressions, attribute-expression channels, `uses:` host templates, chart-type conversion and host support flags, because React charts take already-computed data and ephemeral typed props.

### Principles

- Keep four concerns apart for every chart: stored model and defaults (object-definition), data-shape contract (data targets), editing schema (property/styling/soft definitions) and rendering (renderer definitions, services, models). Each concern gets its own file.
- A property path is the join key across all layers. The panel item `ref`, the JSDoc path, the renderer's getValue(layout, 'dimensionAxis.maxVisibleItems'), the metrics key and the generated spec all use the same path.
- Declare a default once, in the model. Panel defaultValue may be a function of (props, data shape) for context-dependent defaults, and the resolution order is fixed: function > literal > first option > type default.
- A property counts as shared when the same path and the same type appear in several charts. Groups are discovered from paths, not from names, so naming or type drift (gridLine vs gridlines; dataPoint.showLabels boolean vs string) shows up as a defect.
- Compose by reference and override by key; never copy. Name a template or factory, then patch only the differing leaves, or set a leaf to null to remove it. The counter-example is labelStylingDefinition, copied 6 times and differing only by the theme key.
- Parameterize shared factories by section, path, theme key and resolved feature booleans (largePanelSection({ section, getThemeValue }), createMeasureRepresentation(env, enabledFeatures)). Shared code should not know chart ids or feature-flag names.
- Write visibility, validity, read-only state and locking as pure predicates of (stored props, computed data shape). The UI, docs and validation can then evaluate the same rules.
- Normalization and invariants belong in change/globalChange/data-target hooks that run on edit, not in the renderer. When a feature is disabled it still cleans up the data it owns.
- Keep semantic props (grouping, orientation, legend.show) apart from cosmetic overrides, which live in a component-keyed array (components[{ key: 'bar', style }]). Take cosmetic defaults from the theme.
- Offer the same properties in tiers: simple and advanced styling, full panel and reduced soft/explore panel. The tiers share refs, and a view-model adapter (getValue/setPropertyValue/diffs) may map one control onto several fields.
- Effective values can differ from stored values without mutating them. convertFunctions.get overrides (a continuous axis reads as vertical) keep the user's choice for when the context changes back.
- Document properties in the source (JSDoc types, enums, @default, @deprecated, typedefs for reused sub-shapes) and generate the spec and docs from it. Mark internal or UI-only props schemaIgnore.
- Version the property schema and migrate on load through small shared adapters (autoSortAdapter, scrollbarAdapter). Keep deprecated fields documented until they are migrated.
- A cross-cutting feature (scrollbar, trend lines, forecast, custom tooltips, ref lines, plugins, trellis) ships as one module that owns its props, defaults, panel fragment, migration adapter and render helper.

### Transferable

- Shared prop-group modules (type + defaults + resolver per group): Create packages/charts/src/props/ with one file per group from the taxonomy: header.ts (title/subtitle/footnote), legend.ts, category-axis.ts, value-axis.ts, grid.ts, value-labels.ts, reference-lines.ts, tooltip.ts, color.ts, scroll.ts, orientation.ts, trellis.ts. Each file exports `export interface LegendProps { show?: boolean; position?: 'auto'|'top'|'right'|'bottom'|'left'; showTitle?: boolean }`, `export const LEGEND_DEFAULTS = { show: true, position: 'auto', showTitle: true } as const satisfies Required<LegendProps>` and `export function resolveLegend(p: LegendProps | undefined, ctx: ChartContext): Required<LegendProps>`. Chart prop types become intersections: `type BarChartProps = ChartBaseProps & HeaderProps & { legend?: LegendProps; categoryAxis?: CategoryAxisProps; valueAxis?: ValueAxisProps; grid?: GridProps; valueLabels?: ValueLabelProps; referenceLines?: ReferenceLine[]; tooltip?: TooltipProps } & BarSpecificProps`. Your existing charts/legend, charts/tooltip, charts/labels and charts/annotations folders are the render side of these groups; the types and defaults should sit next to them or in props/.
- One canonical name and shape per concept, enforced: Settle every name before centralizing: one `grid` (not gridLine/gridlines), one `valueLabels: { show: boolean | 'auto'; mode?: 'segment'|'total'|'both' }` (not boolean in some charts and string in others), and `referenceLines` vs `categoryReferenceLines` with a shared `ReferenceLineBase { value; label?; show?; color?; lineStyle?: 'solid'|'dashed'; thickness? }`. Charts must use the shared interfaces rather than redeclaring similar ones; an eslint rule or type test can enforce this.
- Layered defaults resolution with computed defaults: `resolveChartProps(def, userProps, ctx)` runs in this order: user prop > per-chart override default > group default > theme token. Computed defaults are functions of the data shape, mirroring bar width 0.9 grouped / 0.7 otherwise / 1 continuous: `defaults: { barWidth: (ctx) => ctx.isContinuous ? 1 : ctx.isGrouped ? 0.9 : 0.7 }`. Expose it as `useResolvedProps(def, props)` inside each chart, memoized on props and data shape, so render code only ever sees Required<> values.
- Per-chart definition object (the React analogue of the stored-definition and extension modules): Every chart exports `barChartDefinition = defineChart({ id: 'bar', dataTargets: { categories: { min: 0, max: (nMeasures) => nMeasures > 1 ? 1 : 2 }, measures: { min: 1, max: (nDims) => nDims > 2 ? 1 : 15 } }, groups: ['header','legend','categoryAxis','valueAxis','grid','valueLabels','referenceLines','tooltip','scroll'], defaults: BAR_DEFAULTS, normalize, controls, metrics })`. From that one object you derive Storybook argTypes (controls), docs tables, runtime dev-mode validation of props and data shape, auto-chart eligibility (the dataTargets min/max act as the data-shape filter for your auto-chart / by-data-shape selector) and a2ui/recipe schemas.
- Normalizers as pure functions (change/globalChange analogue): Replace in-place mutation with `normalize(props, dataShape): props`, called inside the resolver. Examples: clamp maxVisibleItems to [1, 10000/(dims+measures)]; if stacking is impossible fall back from 'butterfly' to 'stacked'; if the axis is continuous, force effective orientation to 'vertical' but keep the user's prop (convertFunctions.get semantics). In dev builds, warn when a prop is ignored in the current context (e.g. `orientation ignored: continuous axis`).
- Visibility / applicability predicates on props: Attach `appliesWhen?: (props, dataShape) => boolean` to each control or prop entry in the definition, e.g. showSegmentLabels only when stacked, measureAxis.min only when !autoMinMax. Use it to hide irrelevant Storybook controls, grey out docs rows, drive a future config/editor form, and emit dev warnings for props that have no effect.
- Parameterized shared factories instead of per-chart copies: Follow the reference table utilities rather than one chart package's duplicated labelStylingDefinition: `createFontStyleResolver({ slot: 'axisTitle' | 'axisLabel' | 'valueLabel' | 'legendTitle' | 'legendLabel', themeKey })` and `<AxisTitle style={resolveFont('axisTitle')}>`. Shared code receives resolved feature booleans (`features: { trendLines: true }`) instead of reading global flags.
- Semantic props vs keyed style slots: Keep semantic props flat and typed (grouping, orientation, legend.show) and put cosmetic overrides in a keyed slot map, `styles?: { bar?: { strokeWidth?: 'none'|'sm'|'md'|'lg'; strokeColor?: string; width?: number }; axisTitle?: FontStyle; axisLabel?: FontStyle; valueLabel?: FontStyle & { contrast?: boolean }; legendTitle?: FontStyle; legendLabel?: FontStyle }`, with one shared `FontStyle { color?; fontFamily?; fontSize?; fontWeight? }`. Defaults resolve from theme tokens per slot; this is the analogue of theme.getStyle('object.barChart', 'axis.title', 'color') and fits the brand-token themes.
- Render-layer extension by key (definitionExtender analogue): Give each chart's internal layers stable keys ('grid', 'bars', 'valueLabels', 'referenceLines', 'tooltip', 'brush'). Accept `layers?: Partial<Record<LayerKey, Partial<LayerConfig> | false>>` or keyed children, so consumers can deep-merge or disable a built-in layer and append new ones, without forking the chart.
- Feature modules own a vertical slice: For reference lines, trellis/small multiples, scroll/navigator, annotations and custom tooltips, give each module one folder that exports `Props` type, `DEFAULTS`, `resolve()`, `normalize()`, the render component/hook, doc metadata and an optional `migrate()`. Charts opt in by listing the module in `groups` and rendering its layer. Your existing charts/navigator, charts/annotations, multiples/ and charts/markers folders are candidates.
- Generate docs/spec from types and a shared-group report: Write TSDoc on the group and chart prop interfaces (@default, @deprecated, union literals), then produce JSON schema per chart with ts-json-schema-generator or the TS compiler API. Port chart-specs' algorithm as a script: flatten each chart's props schema into paths, normalize array indexes, group by path, record the chart set and type union, and emit shared-props.md/json sorted by chart count. Fail CI on (a) the same path with divergent types and (b) near-duplicate names (Levenshtein or singular/plural: gridLine vs gridlines).
- Density tiers (layoutModes analogue): The commons layoutModes (FULL 550x450, MEDIUM 400x220, SMALL 300x150, XSMALL 150x75, SPARK) correspond to your ChartDensity 'xs'|'sm'|'md'|'lg' in charts/chart-config-context.tsx. Let each shared group declare its per-density behavior in one table (legend hidden at sm, tick ceiling at sm, value labels only at lg) inside the group resolver, instead of each chart branching on density.
- Tiered surfaces (simple vs advanced, full vs explore): Tag each prop in the definition with `tier: 'essential' | 'advanced'`. Docs and Storybook show essentials first, and a2ui/recipe generation limits itself to essential props. A view-model adapter (getValue/setValue, like the soft panel's diffs) lets one simplified control such as `labels: 'none'|'auto'|'all'` map onto several underlying props.
- Props versioning and migration adapters: Keep `migrateProps(props)` in dev builds, a small list of adapters that rename deprecated props (e.g. `singleColor` → `color`) and console.warn once. Mark deprecated props @deprecated in TSDoc so docs and editors surface it, and remove adapters on a major version.
- Data-shape contract drives role labels and validation: dataTargets carry role descriptions as a function of shape (bar: first dimension becomes 'Group' when grouped or 'Stack' when stacked; a trailing extra dimension becomes 'Trellis'). Use them to label series in a11y text and legends, to write dev-mode errors like 'bar: max 1 category when >1 measure', and for auto-chart suggestions.

### Not transferable

- The engine's query definition (its paths, dimension and measure lists and their field records, the data mode, the inter-column sort order, the initial data fetch, zero/missing suppression and the others-total spec): They describe a query sent to the reference product's engine, which returns paged, aggregated layouts. A React chart receives already-shaped data arrays plus accessors, so sorting, others-grouping and null suppression happen in the caller's data prep or in explicit props (sort, topN, nullMode). The 246 rows of 12-chart engine paths in shared-properties.md come from expanding the engine schema and should not be copied into a React taxonomy.
- Soft properties (softDefinition, getEffectiveProperties, saveSoftProperties / applyPatches, canSetProperties, onSoftPropertyChange): This is a persistence and permission model: session patches layered over a stored object that the viewer may not be allowed to update. React props are ephemeral and owned by the parent's state. The only transferable part is the idea of an optional controlled/uncontrolled override layer, and plain React state already covers that.
- Engine expressions (value and string expressions, optional expression fields, calculation conditions, colour and measure-range expressions): The engine evaluates these per selection state. In React the caller computes values in JS and passes numbers, strings or functions, e.g. `title: string | ReactNode` and `color: (d) => string`.
- Attribute expressions/dimensions (colorByExpression, colorByAlternative, customTooltip\* ids, refFn to locate them): These are engine-computed per-row side channels addressed by id inside the query definition. The React equivalent is plain accessor props (getColor, getTooltipExtra, series.color), which need no index-finding refFn machinery.
- `uses:` host template registry and the handler/args(layout vs properties) panel runtime: The host client supplies the named panel templates and the panel engine that evaluates show/change/convertFunctions. A React component library has no host panel, so replicate the idea (shared control fragments) only if you build your own editor, and even then as typed TS modules, not string-keyed templates.
- importProperties/exportProperties with the object-conversion module (chart-type conversion, conditionalShow quarantine): This exists to convert a stored host object from one visualization type to another while keeping its engine definition. In React, switching chart type means rendering a different component with the same data and shared group props; shared group types make that free.
- ext.support flags (snapshot, export, exportData, sharing, viewData, effects, modifiers): Host-capability negotiation with the reference product (storytelling snapshots, data export, modifiers computed by the engine). Keep at most an opt-in `exportable`/`snapshot` hook; modifiers such as accumulation or moving average are data transforms the caller or an analytics util should do.
- Object extension and library ids, master items, object info/meta/state-name/layout-exclude records, visualization id: These are the engine's object identity, library linkage and alternate-state bookkeeping, with no meaning in a stateless React component.
- Renderer definitions and brush consumer merging inside definitionExtender: They are specific to the reference renderer's declarative component and brush model. The keyed layer-extension concept transfers; brush-context consumer merging does not.
- Mutating property trees in place (change/globalChange/add/remove hooks mutate data): React needs immutable inputs and pure derivation, so the normalizers must become pure `normalize(props, shape) => props` functions. Mutating props would break memoization and controlled-component semantics.
- Engine-flag gating and isUnsupportedFeature from the host (a host-environment flag): The reference product's runtime environments negotiate features with the host. A React library should use explicit props or build-time exports; at most keep the pattern of passing resolved feature booleans into shared code.
- Telemetry key flattening (extendMetrics `chart_style_*`, `chart_dimaxis_*`): The naming is specific to the reference product's own analytics. The general idea of deriving usage metrics from props in one place is optional and not needed for a unified props model.
