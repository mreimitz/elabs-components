# app-spec.md template

Write this file at the scaffolded app's root. Fill from interview answers;
mark defaulted values with `(default)` so the user sees what was decided for
them. The scaffold is generated FROM this file; later re-runs read it.

`app-spec.md` is **one file for two readers**: the prose below is for humans; a
single fenced `json` block (the **Machine spec**, see below) is the contract
`brand-ui scaffold` consumes. Keep the two in sync. A complete, valid example is
`app-spec.example.md`; the contract is `app-spec.schema.json` (validated by
`brand-ui scaffold`).

```markdown
# App spec — {Title}

> for the scaffold; edit it and re-run the brand-ui-new-app skill to regenerate, or hand it
> to your agent as context.
```

## Machine spec (required — the scaffold contract)

End the file with a single fenced `json` block under a `## Machine spec` heading.
This is what `brand-ui scaffold` reads (the prose above is for humans). It must
satisfy `app-spec.schema.json`:

- **Required:** `archetype` (one of dashboard · data-app · ai-assistant ·
  flow-workspace · settings · marketing), `theme` (slug: light · dark ·
  a custom theme), `title`.
- **Always recorded:** `shell` (flagship · dashboard · mail · double-sided ·
  minimal) — the app shell the screens render in (`app-shells.md`). The CLI
  falls back to `flagship` when it is missing, but the interview always asks.
- **Optional:** `intent` (`purpose`/`audience`/`scale`), `density`,
  `surfaces[]` (`{id, navLabel, archetype}`), `entities[]`
  (`{name, fields:[{name, type, rendersAs?, filterable?}]}`, `type` ∈ text ·
  number · date · status · boolean).

Mirrors the `planScaffold` input in the `@elabs-ai/components-cli` scaffold engine. See
`app-spec.example.md` for a filled-in block; validate any spec with
`brand-ui scaffold <path> --dry-run` (in a consuming project: install
`@elabs-ai/components-cli` — a public npm package, see `docs/CONSUMING.md`
§1 + §7a — then use its bundled schema).
