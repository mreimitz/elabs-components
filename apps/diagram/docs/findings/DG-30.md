# DG-30 — flow particles

The technical canvas now draws a bounded particle layer over the existing flow lines and
under nodes and labels. It uses each edge's actual rounded ELK or fallback SVG path, including
named composite ports. Existing arrowheads, line patterns and `animated` marching dashes remain
independent. No authored field or YAML write is introduced.

## Delivered R1 behavior

| Existing metadata                            | Rendering                                                |
| -------------------------------------------- | -------------------------------------------------------- |
| `real-time`, `continuous`, `stream…`         | Small steady particles, one emission every 600 ms        |
| `hourly`, `every hour…`                      | Three-particle bursts every 2 seconds                    |
| `daily`, `nightly…`, `batch…`                | A larger pulse every 6 seconds                           |
| `on-demand`, `query time`, `when requested…` | Particles while the flow is hovered or keyboard focused  |
| Missing or other schedule text               | A modest steady fallback, one emission every 1.2 seconds |

Schedules remain descriptive strings; these are explanatory visual rhythms, not a wall-clock
scheduler. Data is a dot, request an arrow, access an upright person, control a tick, and network
a faint dash. Forward/back/both follow the authored arrow direction. Both directions emit paired
particles even on short and batch flows. Explicit local Pause/Resume is persisted across tabs
and reloads; reduced motion explains why animation is off. The OS preference and the root motion
preference update live using the existing motion arbitration.

Particles run in the settled technical canvas and isolated component inspection. They stop on
lens transition, pending navigation, hidden documents, pause, reduced motion and unmount. The
visual lens and pure `#v` shared picture have no particle layer or animation control. PNG, SVG
and thumbnail capture exclude the canvas through the existing export marker.

## Implementation boundary

`src/particles` owns profiles, sampled geometry, an imperative Canvas2D engine and local
preference. `DataFlowEdge` exposes its existing schedule as a data attribute. The technical and
drill canvases mount the layer, and `CanvasNavigation` opts into the control through one optional
prop. No shared package or dependency changes.

The engine samples a path only when its `d` changes, caches 64–512 points, and projects those
coordinates through the current viewport transform. Zoom does not resample geometry. Color is
read from the rendered edge's semantic token stroke and refreshed on theme or kind changes.
One screen-sized bitmap is capped at DPR 2; it is pointer-transparent and hidden from assistive
technology. One frame clock is capped at 60 fps. There are at most 240 cached edges and 12
particles per edge, with offscreen-path culling and no per-particle objects during drawing. At
the density limit the oldest trails are omitted; new emissions keep their fixed cadence.

Volume/metrics, visual-lens particles, story-specific particle dimming and published-viewer
integration are outside this R1 slice.

## Validation

The focused pure/engine regressions cover profile fallback, fixed cadence on long paths,
paired directions, geometry sampling and culling, live metadata changes, hover/keyboard demand,
visibility pause and complete listener/observer/clock cleanup.

`tests/particles.mjs` exercises the real app in light/dark at 1440 and 390 pixels: painted canvas
pixels and layering, zoom-cache reuse, persistent pause, live root/OS motion changes, technical
versus visual, child inspection and pure shared-view isolation, unchanged workspace bytes and
zero writes/errors. It also compares PNG bytes with particles enabled/paused and checks SVG
exclusion.

`tests/particles-performance.mjs` measures a real manual diagram with 60 visible flows after a
2-second warm-up. It reports the actual measured cadence and CPU p50/p95/max separately. The
required CPU p95 is at most 4 ms per draw, with at least 45 measured frames per second in the
local Chromium proof. Environment and exact measurements are retained with browser evidence.

The local 2026-09-29 performance run used Chromium 148 headless on macOS, DPR 1, at
1440×1100. With all 60 edges visible and the cap of 720 particles drawn, 275 frames landed in
5.009 seconds (54.9 fps): CPU p50 0.30 ms, p95 0.80 ms, maximum 1.0 ms. These are the measured
local environment results, not a guarantee for every browser or device. The complete app Node
suite passed 406 tests; local TypeScript, lint (11 inherited warnings), production build and
strict audit passed. Independent review rechecked both directions on a short nightly path,
fixed 2-second/6-second cadence on a long path, upright access glyphs, and keyboard controls in
the shipped ClickHouse diagram at desktop/phone widths.
