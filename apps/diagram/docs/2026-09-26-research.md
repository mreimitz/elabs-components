# Architecture diagrams from YAML — research synthesis

Date: 2026-09-26 · Scope: `apps/diagram` (test/demo app, not deployed, not in the standard gates) · Purpose: what exists out there, what the flow package already has, and what that implies for the app and for the flow package later.

Three research threads were run in parallel (diagram-as-code tools, vendor icon licensing, React-Flow-based architecture editors) and cross-checked against the repo. Sources are listed at the end of each section.

**Closest to what we want:** Ilograph (YAML, `children:` nesting, multi-perspective), awsdac (YAML, typed boundary containers, side-pinned links), D2 (terse edge shorthand + icon-by-name + ELK/dagre choice), Eraser (`A > B: label`, `[icon: name]`).

**No React-Flow-based YAML architecture standard exists.** GitHub has only small projects (`bunlongheng/flows`, `draw.albingcj.com`, `dom8509/sysarch`); teams roll their own `nodes/edges` mappers. This is white space — a well-designed YAML dialect on top of brand-ui's flow package would be a first.

### Ten patterns that recur across the good formats

1. **Stable ids ≠ labels** — `id: api`, `title: Order API`; edges refer to ids.
2. **Nesting = containment**, two mechanisms: structural nesting (`children:` — Ilograph, D2, awsdac) _or_ parent reference (`parent: vpc` — FlowSpec v1 already does this). Structural nesting reads better for humans; parent-reference is easier to validate and diff. Support both, normalize to one.
3. **Edge shorthand with inline label** — `a -> b: label` (D2, Eraser). Universal and worth having as sugar over the long form.
4. **Icon by name** resolved against a catalog (`icon: aws/lambda`) — never inline art.
5. **Direction/flow hints, not coordinates** — `direction: LR`; manual `position` only as an override.
6. **Style classes** — declare `styles: { pii: {…} }` once, apply `class: [pii]` many times.
7. **Multiple views over one model** (Structurizr `views`, Ilograph `perspectives`) — same nodes, different filters/emphasis. Out of scope for v1, but the model should not preclude it.
8. **Typed boundaries, not generic boxes** — `AWS::Diagram::VPC`, Structurizr `deploymentNode`: a zone has a _kind_ (account, region, vpc, subnet, on-prem, saas, trust boundary) that drives its look and legend.
9. **Port-side pinning** — `api:R --> L:db` (Mermaid), `SourcePosition: S` (awsdac). Flow already has `handles: {source: Side[], target: Side[]}`.
10. **Text is the source of truth; the picture is a build artifact.** Position persistence must be optional and explicit (`layout: manual` + positions) so auto-layout never fights hand edits.

## 2. Vendor icons and licensing (the part that decides what can live in the library)

Only two "official vendor" sets carry a real OSS redistribution license on the artwork: **Kubernetes icons** (Apache-2.0/CC-BY-4.0, `kubernetes/community/icons`) and by convention the PostgreSQL elephant. Everything else — **AWS Architecture Icons, Azure Architecture Icons, Google Cloud icons, Snowflake, Databricks, ClickHouse, Salesforce, Qlik, SAP, Oracle, Okta/Entra/Auth0** — is licensed for _use in diagrams and documentation_, not for redistribution inside a third-party npm package. Azure's terms forbid using their icons "to represent your own product"; ClickHouse's trademark policy requires logo removal from repackaged distributions.

Aggregators (`simple-icons` CC0, `devicon` MIT, Iconify `logos`, `svgl`) license their _redrawings_ permissively but explicitly disclaim trademark clearance.

This matches brand-ui's existing `ServiceLogo` design exactly (issue #25: the package ships the machinery and a monogram fallback; the _consumer_ registers marks). So:

| Tier                                             | What                                                                                                                                                                                 | Where it may live                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 1 · ships in the library by default              | generic architecture glyphs (server, database, queue, firewall, gateway, user, browser, on-prem building…) from Lucide + a few product-vocabulary icons in `icons`; Kubernetes icons | `@elabs-ai/components-icons` (Lucide already the default)                       |
| 2 · optional community add-on (later, if wanted) | simple-icons / Iconify `logos` redrawings for dev-tool marks, labelled as community redrawings                                                                                       | a separate, opt-in package — not now                                            |
| 3 · consumer-registered only                     | AWS / Azure / GCP official icon packs; Snowflake, Databricks, ClickHouse, Salesforce, Qlik, SAP, Oracle, Okta…                                                                       | the app registers them via `registerServiceLogos`; the library never ships them |
| demo                                             | the demo app may vendor official packs under each vendor's diagram-use terms, kept out of any published package, with a `THIRD_PARTY_ICONS.md` listing the terms                     | `apps/diagram/public/icons/**` (private, never published)                       |

**Maintainer ruling 2026-09-26:** the analysis above governs the library packages. Inside `apps/diagram` all brands and trademarks may be used freely, and nothing from that folder is added to `ATTRIBUTION.md`.

Consequence for the YAML: `icon:` is a _name_ (`aws/lambda`, `azure/functions`, `qlik/cloud`, `lucide/database`) resolved through a registry the app supplies. The library defines the naming scheme and fallback, not the artwork.

## 3. React Flow v12 facts that shape the design

- **Nesting**: `parentId` + `extent: "parent"`, arbitrary depth, parents must precede children in the array; child coordinates are parent-relative. The flow package's `useFlowGroups` / `FlowGroupNode` already wrap this.
- **Parents do not auto-size to children** — needs `getNodesBounds()` + padding, done by us. Not in the flow package yet.
- **Drag re-parenting** (drop a service into another zone) is DIY via `getIntersectingNodes`.
- **Layout**: dagre has no compound support; ELK `layered` with `elk.hierarchyHandling: INCLUDE_CHILDREN` + `elk.padding` per container is the right engine. **`layoutFlowElk` in the flow package already does exactly this** (`groups: [{id, children}]`, header offset, `INCLUDE_CHILDREN`), so the hard part exists.
- **Container-to-container edges**: React Flow expects handles on leaves; the pattern is a floating edge computed against the container's rectangle. `FlowFloatingEdge` exists.
- **Obstacle-avoiding orthogonal edges**: `@tisoap/react-flow-smart-edge` (A\* grid, MIT, 361★) is the reference implementation; `FlowSmartEdge` exists in the package — its avoidance quality must be checked against architecture-scale diagrams.
- **Export**: `html-to-image` (pin 1.11.11) + `getNodesBounds` + `getViewportForBounds` is the canonical PNG/SVG recipe; vector clipboard via `ClipboardItem` with an SVG blob. Charts has PNG/SVG export (`ChartFrame`, RM-042); flow has none.
- **Swimlanes/bands**: no primitive — full-width group nodes at `zIndex: -1` per band ("Client managed" / "SaaS" / "Hosted"). A legend is a non-graph overlay; `Legend` exists in flow.
- **Round trip**: store `position` only when `layout: manual`; on YAML edit, parse → diff → patch nodes (don't replace) → re-run ELK for unpositioned nodes; error lines via a position-keeping parser (`yaml` npm, as the 2026-09-25 review already decided).

The main takeaway: **the hard engine pieces exist (nested ELK layout, group nodes, custom node primitives, floating/smart edges, definition base). What is missing is the domain layer** — architecture node kinds, typed zones, data-movement edges, an icon-name scheme, the YAML dialect, the spec core, the inspector form, and export.
