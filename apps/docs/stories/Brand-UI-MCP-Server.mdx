# brand-ui MCP Server

`brand-ui mcp` is a **persistent, dependency-free Model-Context-Protocol server**
that exposes the brand-ui CLI engine to coding agents — so an agent gets brand-ui
ground truth **in any session, with the Storybook dev server down**. It is the
always-on complement to the [Storybook MCP](?path=/docs/docs-storybook-mcp-for-agents--docs),
which only exists while `pnpm storybook` runs.

## Connect by URL — nothing to install

The lookup tools are **hosted** at `https://elabs-ai.com/mcp` (stateless Streamable
HTTP, answered from the manifest of the latest release). Any MCP client can use it:

```bash
claude mcp add --transport http brand-ui https://elabs-ai.com/mcp
```

```json
{ "mcpServers": { "brand-ui": { "type": "http", "url": "https://elabs-ai.com/mcp" } } }
```

The hosted server serves `info`, `search`, `docs`, `tokens`, `chart_for` and `a2ui`. Two things
stay local, because they read **your** files: `audit` (lints your source) and your
project's own **taste profile** (`brand-ui.config.json`). For those, run the same server
over stdio in your project — the next sections.

|                 | **brand-ui MCP** (this page)                                                    | **Storybook MCP**                                         |
| --------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Source of truth | the committed `brand-ui.manifest.json`                                          | the live-rendered stories                                 |
| Availability    | **always** (no dev server)                                                      | only while `pnpm storybook` runs                          |
| Best for        | the API: props, variants, intent, tokens, search, static audit                  | the **rendered** view: previews, interaction + a11y tests |
| Transport       | HTTP (`https://elabs-ai.com/mcp`) or stdio (`npx @elabs-ai/components-cli mcp`) | HTTP (`localhost:6006/mcp`, dev only)                     |
| Tool prefix     | `mcp__brand-ui__*`                                                              | `mcp__storybook__*`                                       |

> Rule of thumb: reach for **brand-ui MCP** to know _what exists and how to use it_
> (anti-hallucination), and **Storybook MCP** to _see it render and test it_. When
> both are up, use both; when Storybook is down, brand-ui MCP still answers.

## How it works

```
your component source ──pnpm gen───────▶ brand-ui.manifest.json ──▶ brand-ui MCP ──▶ agent
                         (committed artifact, CI-gated)            (reads it live)
```

The server is a thin **transport over the engine** — it re-reads
`brand-ui.manifest.json` on every call (`loadManifest`), so it never serves stale
data once the manifest is regenerated, and never needs a restart. The manifest is a
committed, deterministic artifact kept fresh automatically:

- a **pre-commit hook** regenerates + stages the manifest when component/token/registry
  inputs change,
- the **`pnpm gen:check` CI step** fails the build if the committed manifest is stale,
- the `/new-component` & `brand-ui-component` workflows run `pnpm gen`.

So adding or changing a component flows to the MCP automatically — there is nothing to
hand-maintain. (During active dev, run `pnpm gen` to reflect _uncommitted_ edits
immediately.)

The protocol is plain newline-delimited JSON-RPC 2.0, implemented directly (no SDK
dependency), so `@elabs-ai/components-cli` stays dependency-light and runs in any consuming project.

## The tools

| Tool        | Arguments                   | Returns                                                                                                                                                                                                                                   |
| ----------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `info`      | —                           | which `@elabs-ai/components-*` packages are present, themes + default, token count, registry size. Call once per session.                                                                                                                 |
| `search`    | `query`                     | components/hooks/registry items matching a name or concept — **before** writing UI.                                                                                                                                                       |
| `docs`      | `component`                 | the real API: own-declared props (type/default/description), **expanded** cva variant values, per-component intent (purpose/relationships/anti-patterns), resolved inherited props when enriched. Never guess props.                      |
| `tokens`    | —                           | the theme/token summary: themes, default theme, base radius, semantic token count.                                                                                                                                                        |
| `chart_for` | `shape`                     | ranks the `@elabs-ai/components-charts` containers for a data shape ("weekday by hour ticket volume") — call it before picking a chart type by hand.                                                                                      |
| `a2ui`      | `verb`, `type`?, `surface`? | generative UI: `catalog` (the types an agent may emit, or one in full), `schema` (JSON Schema), `validate` (every problem in a surface, with its path), `example`. See [Generative UI (A2UI)](?path=/docs/docs-generative-ui-a2ui--docs). |
| `audit`     | `path`                      | static token/style/anti-slop lint of a file or directory — **local server only**. (The rendered cross-theme + WCAG pass lives in the `brand-ui-audit` skill.)                                                                             |

## Set it up

**In the monorepo** — already wired in repo-root `.mcp.json` under the server name
`brand-ui`:

```json
{
  "mcpServers": {
    "brand-ui": {
      "type": "stdio",
      "command": "node",
      "args": ["packages/cli/bin/brand-ui.mjs", "mcp"]
    }
  }
}
```

Confirm it's connected in Claude Code with `/mcp` (a session reload may be needed). The
tools then appear as `mcp__brand-ui__info`, `mcp__brand-ui__docs`, etc.

**In a consuming project** — run the published CLI (the brand-ui plugin ships this entry
automatically). `@elabs-ai/components-cli` is public on npmjs.org, so `npx` resolves it
with no registry setup and no token:

```json
{
  "mcpServers": {
    "brand-ui": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@elabs-ai/components-cli", "mcp"]
    }
  }
}
```

Or add it from the CLI:

```bash
claude mcp add brand-ui --scope project -- npx -y @elabs-ai/components-cli mcp
```

## Try it without an agent

The hosted server answers plain JSON-RPC over HTTPS:

```bash
curl -s https://elabs-ai.com/mcp -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"docs","arguments":{"component":"Button"}}}'
```

The local server speaks stdio, so you can drive it with a pipe:

```bash
printf '%s\n%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"docs","arguments":{"component":"Button"}}}' \
  | npx @elabs-ai/components-cli mcp
```

The ready banner prints to **stderr** (stdout carries only the JSON-RPC stream, so it
isn't corrupted).
