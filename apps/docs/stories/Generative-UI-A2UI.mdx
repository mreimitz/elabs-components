# Generative UI (A2UI)

Most screens are **built with** brand-ui: you or your coding agent write the code (D1).
Sometimes the agent must **design the screen at runtime** — an order card for the order
the user just asked about, a KPI row for this question, a form for the details the agent
still needs. That is generative UI, and brand-ui's answer is A2UI: **the agent describes
the screen as data, brand-ui validates it against a catalog and renders it with the real
components.** No JSX from the model, no `eval`, no agent styling — a surface always wears
your theme.

The card above is not code an agent wrote. It is this JSON, rendered by `<A2uiSurface>`:

```json
{
  "a2ui": "1",
  "title": "Order 4711",
  "root": {
    "type": "Card",
    "children": [
      { "type": "CardHeader", "children": [{ "type": "CardTitle", "children": ["Order 4711"] }] },
      {
        "type": "CardContent",
        "children": [
          {
            "type": "Grid",
            "props": { "columns": 3 },
            "children": [
              {
                "type": "MetricCard",
                "props": {
                  "label": "Total",
                  "value": 1240,
                  "valueFormat": "currency",
                  "currency": "EUR"
                }
              },
              { "type": "StatusBadge", "props": { "status": "awaiting-approval" } }
            ]
          }
        ]
      },
      {
        "type": "CardFooter",
        "children": [
          {
            "type": "Button",
            "on": { "click": { "name": "approve", "payload": { "id": 4711 } } },
            "children": ["Approve"]
          }
        ]
      }
    ]
  }
}
```

## The protocol

A surface is `{ "a2ui": "1", "title"?, "root": node }`. A node is a **string** (text) or
an element:

| Key        | What it is                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ |
| `type`     | A catalog type — `"Card"`, `"Button"`, `"Stack"`, … Anything else fails validation.                                      |
| `props`    | Checked against that type's schema: unknown props, enum values and required props are errors. Never `className`/`style`. |
| `children` | Child nodes, only for types that take them (`Card`, `Stack`, `TableRow`, …).                                             |
| `on`       | Event bindings from the type's vocabulary (`click`, `change`) to an **action**: `{ "name": "approve", "payload"?: … }`.  |
| `id`       | Optional stable id, rendered as `data-a2ui-id` so the host can address the node.                                         |

Props the catalog types as `node` (`SectionHeader.title`, `.actions`, `MetricCard.label`)
take text, one element, or a list of elements — so an agent can put a `Badge` in a header's
action slot without a special case.

## Interaction stays with your app

A surface cannot call anything. `on.click` names a **host verb**; your `onAction` decides
what "approve" means — a mutation, a navigation, a message back to the model (D5). Change
events carry the control's value.

```tsx
import { A2uiSurface } from "@elabs-ai/components-ai";

<A2uiSurface
  surface={toolResult.surface}
  onAction={(action, { event, value }) => {
    if (action.name === "approve") approveOrder(action.payload.id);
    if (action.name === "set-carrier") setCarrier(value);
  }}
/>;
```

## Streaming and errors

Pass the JSON **text** as it arrives with `isStreaming`. The surface completes the partial
document, draws every node that already validates and prunes the rest — nothing errors
until the input settles. A settled surface that breaks the contract renders a
`role="alert"` listing every problem with its path and fires `onError` once, so an agent
can repair its own output from the message.

## The catalog

What an agent may emit is a promise, so the list is small and real: the layout builtins
`Stack` and `Grid` (drawn by the surface on tokens) plus the `@elabs-ai/components-ui`
types below. Props come from the manifest's real prop tables and cva variants — a variant
is valid the day the component has it, and never before. Agents read the same table with
`brand-ui a2ui catalog [<Type>]` or the hosted MCP's `a2ui` tool.

## Extend it with your own types

`ai` may not import its sibling packages, so a chart, a map or a domain card joins the
catalog **in your app**: bind the component, describe its props, and pass the catalog.
Anything you add must render on semantic tokens so a surface keeps inheriting the theme.

```tsx
import {
  A2UI_CATALOG_SCHEMA,
  UI_CATALOG_BINDINGS,
  createA2uiCatalog,
  defineA2uiType,
} from "@elabs-ai/components-ai";
import { Sparkline } from "./sparkline";

const catalog = createA2uiCatalog(
  { ...UI_CATALOG_BINDINGS, Sparkline },
  {
    ...A2UI_CATALOG_SCHEMA,
    Sparkline: defineA2uiType({
      summary: "A tiny bar sparkline for a short numeric series.",
      props: {
        label: { type: "string", required: true },
        points: { type: "array", required: true },
      },
    }),
  },
);

<A2uiSurface surface={surface} catalog={catalog} />;
```

## Charts, KPI cards and infographics

Analytics is where an agent-designed screen earns its keep: the question decides the
picture. `@elabs-ai/components-charts` ships its half of the catalog — `AutoChart` (one
serializable `ChartSpec`, the mark inferred when `type` is omitted), `ChartCard`,
`MetricGrid`, `Sparkline`, `BulletChart`, `Gauge` — and an app merges it with the ui half.
The KPI cards and infographics from the registry join the same way, through **adapters**:
the agent emits facts (actual, target, prior year, a weekly series) and the block derives
bands, deltas and pace exactly as it always has, so a model can never type a delta that
disagrees with the numbers.

```tsx
import {
  A2UI_CATALOG_SCHEMA,
  UI_CATALOG_BINDINGS,
  createA2uiCatalog,
} from "@elabs-ai/components-ai";
import { CHARTS_A2UI_BINDINGS, CHARTS_A2UI_CATALOG_SCHEMA } from "@elabs-ai/components-charts";

const catalog = createA2uiCatalog(
  { ...UI_CATALOG_BINDINGS, ...CHARTS_A2UI_BINDINGS, KpiHero, GapToBenchmark },
  {
    ...A2UI_CATALOG_SCHEMA,
    ...CHARTS_A2UI_CATALOG_SCHEMA,
    KpiHero: kpiHeroType,
    GapToBenchmark: gapType,
  },
);
```

## The agent's loop

1. **Read the catalog** — `brand-ui a2ui catalog` (or the MCP `a2ui` tool with
   `verb: "catalog"`); one type in full with `catalog <Type>`.
2. **Emit the surface** as a tool result or message part. For structured-output modes,
   `brand-ui a2ui schema` prints the JSON Schema (also published as
   `@elabs-ai/components-ai/a2ui/schema.json`).
3. **Validate** — `brand-ui a2ui validate <file>`: one `path code message` line per problem,
   exit 1 when invalid. The renderer runs the same validator.
4. **Render** with `<A2uiSurface surface onAction />`; resolve actions in the app.

## Where it sits (D2)

| The agent is producing…                 | Render with                                            |
| --------------------------------------- | ------------------------------------------------------ |
| A conversation (text, tools, reasoning) | AI SDK `UIMessage` + the chat components — the default |
| **A screen it designed** (UI as data)   | **A2UI** — `<A2uiSurface>`, this page                  |
| Ad-hoc JSX as a string                  | `JSXPreview` — the escape hatch; flexible, less safe   |

A chat that only shows messages is still build-with. Reach for A2UI when the agent must
decide what the screen contains. The full contract, including the other two paths, is on
[AI Output Contract for Agents](?path=/docs/docs-ai-output-contract-for-agents--docs);
the routing decision lives in `docs/DECISIONS.md` §D2.
