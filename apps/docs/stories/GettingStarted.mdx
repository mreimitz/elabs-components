# Getting Started

`brand-ui` is a **source-owned, token-driven** React component system. This page is
the **front door**: pick the workflow that matches what you're doing, run the
commands, and follow the deep links for detail. It is honest about what's turnkey
today and what still needs a manual step.

## Pick your path

| I want to…                                     | Go to                                                    | Needs                              |
| ---------------------------------------------- | -------------------------------------------------------- | ---------------------------------- |
| **Start a brand-new app** with an AI assistant | [Path A](#path-a--start-a-new-app-in-claude-code)        | Claude Code + the plugin           |
| **Add brand-ui to an app I already have**      | [Path B](#path-b--add-brand-ui-to-an-existing-app)       | GitHub Packages access + a bundler |
| **Make my coding agent brand-ui-aware**        | [Path C](#path-c--make-your-coding-agent-brand-ui-aware) | the plugin _or_ the agent kit      |
| **Work inside this monorepo**                  | [Path D](#path-d--work-inside-this-monorepo)             | `pnpm install`                     |

> **The one thing to know first: this is _not_ on the public npm registry.**
> `npm install @elabs/components-ui` **404s** there — the packages are
> `private` and published to **GitHub Packages** instead. You need a one-time
> `.npmrc` scope mapping + a `read:packages` token to install them; after that
> they behave like any other npm dependency (real semver, lockfiles, `pnpm update`).
> Everything below reflects that. (Full detail:
> `docs/CONSUMING.md`.)

## The bundled offering — the five pieces and where each lives

| Piece                                                                                                                                                                                                                                                                                                    | What it is                                                                                    | How you get it                               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------- |

| **The registry**                                                                                                                                                                                                                                                                                         | copy-own block/template JSON (`shadcn add`)                                                   | **self-hosted** JSON (see Path B step 5)     |

## Path A — Start a new app in Claude Code

The fastest "zero to on-brand app" route. You drive it in natural language; the
plugin's skills do the work.

1. **Install the plugin** (once per machine):

   ```text
   /plugin marketplace add <path-to-this-repo>
   ```

   This registers the skills, the reviewer agents, and both MCP servers (see Path C).

2. **Say what you want to build.** `brand-ui-start` is the concierge — it routes
   "build me a sales dashboard" / "I need an admin console" to **`brand-ui-new-app`**,
   which runs a short interview, writes a reviewable **`app-spec.md`**, then
   **scaffolds from the matching template** — app code, the root wiring
   (`@elabs/components-tokens` styles + `<ThemeProvider>` + Tailwind `@source` lines), and a
   **starter `CLAUDE.md`** so later sessions stay on-brand.

3. **Make it run.** The scaffold is _code_; to actually start it you still install
   the component packages from GitHub Packages — that's **Path B**. If you
   scaffold **inside this monorepo** (`apps/`), the workspace already provides
   them and it runs immediately.

> **Status / gap:** the interview + template scaffold are shipped; the deeper
> spec-driven file-emitting scaffold engine (the CLI `scaffold` command) is still
> evolving (VP-02). And the new-app flow doesn't yet automate the Path B GitHub
> Packages install (`.npmrc` + token) for a _standalone_ project — you do that
> step yourself today.

## Path B — Add brand-ui to an existing app

Four steps. This is the condensed version; the authoritative, copy-pasteable guide
(peers, Next.js, troubleshooting, upgrading) is
`docs/CONSUMING.md`.

**1 · Authenticate, then install the packages (GitHub Packages, not the public
registry).** Add the `@elabs` scope mapping to your project's `.npmrc`:

```ini
@elabs:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

Provide `GITHUB_TOKEN` (a **classic** PAT with `read:packages` — fine-grained PATs
don't reliably work against GitHub Packages). Then install like any normal
dependency:

```bash
pnpm add @elabs/components-tokens @elabs/components-ui
```

No `file:` deps and no `pnpm.overrides`/`resolutions` mirror block needed — real
registry resolution handles cross-package peers. (All packages are **ESM-only**.)

**2 · Wire Tailwind v4 + tokens** in your CSS entry — the first two lines are
required; the reference themes are opt-in:

```css
@import "@elabs/components-tokens/styles.css"; /* Tailwind + token→utility map + :root base + fonts */
@source "../node_modules/@elabs/components-ui/dist"; /* one @source per @brand pkg you render */

/* Opt-in reference themes. Import the ones you want, or none and ship your own. */
@import "@elabs/components-tokens/themes/light.css";
@import "@elabs/components-tokens/themes/dark.css";
```

> **The #1 consumer mistake:** skip the `@source` line and components render
> **completely unstyled**. Tailwind doesn't scan `node_modules` unless you tell it to.

> `styles.css` alone renders correctly — `:root` is a complete neutral light
> palette. A `[data-theme="…"]` only applies once its stylesheet is imported.
> Writing your own theme: `docs/CONSUMING.md` §5.1.

**3 · Add the bundler plugin.** Vite: `@tailwindcss/vite`. Next.js: `@tailwindcss/postcss`.

**4 · Wrap the app root** in `ThemeProvider`:

```tsx
import "@elabs/components-tokens/styles.css";
import { ThemeProvider } from "@elabs/components-tokens";
import { Button, Card } from "@elabs/components-ui";

export default function App() {
  return (
    <ThemeProvider defaultTheme="light">
      <Card>
        <Button>Click me</Button>
      </Card>
    </ThemeProvider>
  );
}
```

**5 · (Optional) Copy-own blocks via the registry.** Some prototype compositions
are meant to be _copied into your repo_ to edit freely, with `components.json`
configured:

```bash
npx shadcn add https://<your-own-host>/ai-chat-shell.json
```

> **Status / gap:** the registry isn't hosted for you — `<your-own-host>` is a
> placeholder for a host YOU control. Self-host the built JSON
> (`pnpm dlx shadcn build registry/registry.json`) and serve it from there, or skip
> hosting entirely and copy block source straight from `registry/blocks/<name>/`.
> Most consumers only need the imported packages (steps 1–4); reach for copy-own
> only for one-off prototype blocks.

## Path C — Make your coding agent brand-ui-aware

Components alone don't tell an AI agent **what exists or how to compose it**. Add the
agent layer so it uses the real inventory instead of guessing.

- **Claude Code / Cowork** — install the plugin (Path A step 1). It ships the
  skills, the reviewer agents, and **two MCP servers**:
  - **`brand-ui`** (always-on) — the **API** ground truth (`info`/`search`/`docs`/
    `tokens`/`audit`), works with Storybook down. See
    [Docs / brand-ui MCP Server](?path=/docs/docs-brand-ui-mcp-server--docs).
  - **`storybook`** (while `pnpm storybook` runs) — the **rendered** view (previews,
    interaction + a11y tests). See
    [Docs / Storybook MCP for Agents](?path=/docs/docs-storybook-mcp-for-agents--docs).
- **Other harnesses** (Cursor, Copilot, Gemini) — vendor the **agent kit** zip
  (sanitized `skills/` + `brand-ui.manifest.json` + `llms.txt`) and point the tool at
  `llms.txt`.
- **The CLI** — install `@elabs/components-cli` from GitHub Packages (same auth as
  Path B step 1: `.npmrc` scope mapping + a `read:packages` PAT), then the
  skill's commands work in your project:

  ```bash
  pnpm add -D @elabs/components-cli
  pnpm exec brand-ui info            # themes, tokens, the @elabs/components-* packages you have
  pnpm exec brand-ui search <query>  # find a component / hook / registry item
  pnpm exec brand-ui docs <Name>     # real props + intent — never guess the API
  ```

> **Status / gap:** `brand-ui …` / `@elabs/components-cli …` only resolve **after** you install
> `@elabs/components-cli` — it is a private GitHub Packages dependency, not on the
> public npm registry. Inside Claude Code with the plugin **and the `@elabs`
> scope authenticated**, prefer the `mcp__brand-ui__*` tools instead.

## Path D — Work inside this monorepo

```bash
pnpm install        # all packages, workspace-linked
pnpm storybook      # this docs site (+ the Storybook MCP)
pnpm playground     # the Vite demo app
pnpm build          # tsup → dist/ for every package
```

Import across packages via the `@elabs/components-*` alias (never relative paths). Scaffold a
new component end-to-end with `/new-component <pkg> <Name> "<purpose>"`; it writes the
`tsx`/`index.ts`/`stories`/`test`, adds the barrel export, and refreshes the manifest.

## Theming basics

Theming is the `data-theme` attribute + semantic tokens — components never hardcode
colors, they reference tokens (`bg-background`, `text-muted-foreground`,
`border-border`). Two themes ship: **light** (default), **dark**,
**blueprint**. In these docs, switch with the **theme** toolbar control (and try the
orthogonal **Decoration**, **Density**, **Motion** dials). In an app, wrap the tree in
`ThemeProvider` and read/set with `useTheme()`. Re-branding is a token change in
`@elabs/components-tokens` `themes.css`, never a component change.

## Build with tokens, not raw colors

The one hard styling rule: **semantic, token-backed utilities only** — `bg-card`,
`text-foreground`, `border-border`, `bg-primary`, `ring-ring`, … — never a raw hex /
`rgb()` / arbitrary color outside `themes.css`. That's what keeps every component
correct across both themes for free. `brand-ui audit <path>` catches violations.
