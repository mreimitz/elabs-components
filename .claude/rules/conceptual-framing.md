# Conceptual framing (pick the right model first)

Open-ended/structural work (a theme, a system-wide visual change, a new capability) must not
solve the **wrong model** well:

## Re-frame trigger (most important)

- User corrects the **same dimension twice** → STOP patching. Re-derive the deliverable from
  their GOAL and question your architecture out loud; no point fix and no success claim until
  the frame is re-validated.

## Explore alternatives before scaffolding

- Before committing an architecture (package / components / mechanism): **2–3 conceptually
  distinct approaches**, scored against the real success criterion, never ease of building.
- **Prefer systemic / automatic** (a token/theme re-encoding every consumer gets free) over
  **additive, opt-in parts**. A "theme" that needs widgets dropped on each screen is the wrong
  model: a theme re-encodes the semantic system into another channel, not a kit of parts.

## Clarifying questions offer concepts, not parameters

- A direction question for net-new design MUST offer **alternative concepts**, not parameters
  _within_ a model you already picked.

## Don't manufacture false rigor

- Green typecheck/lint/tests prove conformance to a spec, not that the spec is right. Validate
  the **concept against the goal** on a real surface (@.claude/rules/quality-gates.md,
  Theme-safe) BEFORE the implementation against the spec.
